# ADR-006 메인 세션 도구 제한

- main Bash: **ran** (2/2 runs) · worker Bash: **ran 0/2 runs 확인**(파일 생성 기준으로는 실패로 관측)

  두 번 실행(같은 워크플로 `spike-6-allowed-tools.yml`을 연속 재실행, 아래 표 참조) 모두 `main_bash: "ran"`으로 동일했다. `/spike-restricted` 커맨드의 frontmatter `allowed-tools: Workflow(spike-hooks)`는 메인 세션의 직접 Bash 호출(`echo MAIN_SESSION_BASH_RAN`)을 막지 못했고, hooks.log에도 `PreToolUse Bash echo MAIN_SESSION_BASH_RAN`이 정상 기록됐다. `permission_denials: []`(두 번 다) — 즉 CLI 입장에서는 이 호출이 "허용된" 것으로 처리됐다(ADR-002와 동일하게 `--permission-mode dontAsk`가 우선).

  | run | main_bash | worker 파일(.spike/worker-*.txt) | SPIKE_WORKER_BASH hook 줄 | subagent_stats.spawned | num_turns | duration_ms |
  |---|---|---|---|---|---|---|
  | 1회차 (34574564725) | ran | 0개 | 0 | 0 | 1 | 1398 |
  | 2회차 (34574709197, 재실행) | ran | 0개 | 1 | 0 | 1 | 2032 |

  두 번 다 SubagentStart/SubagentStop hook은 워커 2명분(2줄씩) 정상 발화했지만(ADR-001과 동일한 훅 관측), 워커가 실제로 `.spike/worker-<n>.txt`를 쓰거나 `echo SPIKE_WORKER_BASH_<n>`을 완주하기 전에 `Stop`이 발화하며 세션이 끝났다. 워크플로 결과 JSON도 `workers: [{"n":1,"done":false},{"n":2,"done":false}]`로 **워커가 스스로 미완료를 보고**했고, top-level `subagent_stats.spawned`는 0(훅이 관측한 SubagentStart 2건과 모순 — 동일 환경에서 상위 집계 필드와 훅 이벤트 사이에 불일치가 있음). `.result`의 `origin.kind`가 `"task-notification"`으로, 이 run에서 `-p`가 백그라운드로 넘어간 워크플로의 완료를 동기적으로 기다리지 않고 알림 형태로 조기 반환했다는 정황과 일치한다. Task 7(spike-idle)에서도 동일 CLI(2.1.268)로 같은 패턴(빠른 반환, `duration_ms` 수 초, 실제 백그라운드 작업 미완료/미확인)이 관측됐다 — 이는 allowed-tools 질문과 별개로 **이 환경에서 `agent()`/`parallel()`로 스폰된 서브에이전트가 `-p` 프로세스에 의해 안정적으로 동기 대기되지 않는다**는 교차 스파이크 신호이며 별도 후속 스파이크가 필요하다(본 스파이크 범위 밖).

- ADR-008과의 교차 검증(브리프 요청): ADR-008은 project-only/cli-settings 모드에서 `permissions.deny`가 있으면 Bash 전체가 봉쇄되고(echo까지 거부), trusted 모드에서만 allow가 정상 작동하며 deny가 선택적으로 걸린다는 것을 보였다. 본 스파이크(spike-6)는 `.claude/settings.json`에 deny가 이미 추가된 상태(Task 11 이후)에서 실행됐고 **workspace는 untrusted**였다. ADR-008의 project-only 결과대로라면 Bash 전체가 봉쇄돼 `main_bash: "denied"`가 나와야 하는데, 실제로는 `main_bash: "ran"`이었다 — 차이는 `spike-deny`(ADR-008)가 실제로 deny 패턴(`git push --force`)을 트리거해야 거부 로직이 발동하는 반면, `spike-restricted`의 `echo MAIN_SESSION_BASH_RAN`은 deny 패턴에 전혀 해당하지 않는 일반 Bash 호출이라는 점이다. 즉 이번 결과로 보아 "deny 존재 시 Bash 전면 봉쇄"는 **deny 패턴과 실제로 매치되는 호출이 있었던 run에서만 관측된 부작용(혹은 세션별 비결정성)**이었을 가능성이 있어, ADR-008의 결론을 100% 일반화하기엔 조심스럽다. 어느 쪽이든 이번 spike-6 결과 자체는 **command frontmatter의 `allowed-tools`가 메인 세션의 Bash를 게이트하지 못했다**는 점은 명확하다 — 실제로 메인 세션을 게이트하는 것은 (a) `--permission-mode`(dontAsk가 최우선으로 통과시킴), (b) 존재한다면 workspace-trust 여부와 결합된 `permissions.deny`(ADR-008)이며, command-level `allowed-tools`는 이 두 메커니즘보다 하위에 있다.

- **결정**: 커맨드 `allowed-tools`로 메인 세션을 잠그는 방식은 **채택하지 않는다** — `--permission-mode dontAsk` 하에서 무력하다(2/2 재현). 대신 **verify-stage 사후 검증**(예: 워커가 생성해야 할 파일 존재 여부, hooks.log의 `agent_id` 유무로 메인 세션 vs 서브에이전트 발화 구분)과 ADR-008에서 확정한 **trust 부트스트랩 + project `permissions.deny`** 조합으로 실질적인 게이트를 건다. 단, 이번 관측에서 워커의 서브에이전트 실행 자체가 신뢰성 있게 완료되지 않았으므로(2/2 run에서 워커 파일 0개), verify-stage 사후 검증을 채택하기 전에 서브에이전트 동기 대기 신뢰성 문제(위 교차 발견)를 별도로 해결해야 한다는 전제 조건을 남긴다.
