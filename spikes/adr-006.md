# ADR-006 메인 세션 도구 제한 (신뢰된 워크스페이스)

- 실행: `spike-6b-allowed-tools-trusted.yml` (run [34576277839](https://github.com/LeeHyeonKyu/know-thy-build-demo/actions/runs/34576277839)), 워크스페이스는 `trust-workspace` action으로 사전에 trusted 처리, 3개 매트릭스 레그 모두 성공(success)으로 종료.

  | mode | elapsed | main_bash(self-report) | main Bash in `permission_denials` | main bash hook line(`MAIN_SESSION_BASH_RAN`) | worker files (.spike/worker-*.txt) | worker bash hook lines(`SPIKE_WORKER_BASH`) | `Ignoring` 경고 |
  |---|---|---|---|---|---|---|---|
  | frontmatter | 9s | ran | 0 | 1 | 2/2 | 0 | 없음 |
  | cli-allowed (`--allowedTools Workflow(spike-hooks)`) | 11s | ran | 0 | 1 | 2/2 | 2 | 없음 |
  | cli-disallowed (`--disallowedTools Bash`) | 20s | **denied** | 0 | **0**(훅 자체가 안 찍힘 — 호출이 발화 전에 거부됨) | 2/2(단, workers 모두 `done:false` 자기보고) | **0** | 없음 |

  **`permission_denials`는 세 레그 모두 빈 배열 `[]`** — 브리프가 판정 1순위로 제시한 "메인 세션의 Bash가 `permission_denials`에 있는가" 기준은 **이 CLI 버전에서 단 한 번도 채워지지 않아 사용할 수 없다**(ADR-006 구버전 관측과 동일). 대신 (a) `.result` 안의 `main_bash` 자기보고, (b) hooks.log에서 `MAIN_SESSION_BASH_RAN` 훅 라인의 존재/부재로 실질 판정했다.

  - **frontmatter**(`allowed-tools: Workflow(spike-hooks)`): 훅에 `MAIN_SESSION_BASH_RAN`이 정상 기록되고 `main_bash: "ran"` — frontmatter는 메인 세션 Bash를 전혀 막지 못했다. 브리프 표의 "frontmatter | no | yes → grant일 뿐 restrict 아님" 행과 일치.
  - **cli-allowed**(`--allowedTools Workflow(spike-hooks)`): frontmatter와 동일하게 `main_bash: "ran"`, 훅 라인도 찍혔고 워커도 Bash까지 완주(`SPIKE_WORKER_BASH` 2줄, `done:true` 2/2). **브리프가 기대한 "cli-allowed | yes | yes"(메인만 제한) 행과 다르다** — `--permission-mode dontAsk` 하에서는 `--allowedTools`가 화이트리스트로 좁히는 효과 없이 그냥 무해했다. dontAsk가 모든 허가 질의를 우회하므로 allow 목록 자체가 게이트로 작동하지 않는 것으로 보인다.
  - **cli-disallowed**(`--disallowedTools Bash`): `main_bash: "denied"`이고 `MAIN_SESSION_BASH_RAN` 훅 라인 자체가 찍히지 않았다(호출이 훅 발화 전 단계에서 거부됨) — 메인 세션 Bash는 확실히 막혔다. 그런데 **서브에이전트도 함께 막혔다**: `SPIKE_WORKER_BASH` 훅 라인 0개, 워크플로 결과의 `workers`가 둘 다 `done:false`로 자기보고(3단계 중 Bash를 쓰는 2단계에서 막혀 미완료). `.spike/worker-*.txt` 파일은 2개 다 존재하는데, 이는 워커의 1단계(`Write`)까지는 실행됐기 때문이며 **Write는 `--disallowedTools Bash`의 영향을 받지 않았을 뿐**이지 "서브에이전트가 자유롭다"는 증거가 아니다. 즉 브리프의 "worker files 2개 = 서브에이전트 자유" 판정 기준은 이번 케이스에서 오도적이며, 더 정밀한 신호(`SPIKE_WORKER_BASH` 훅 라인 수, `done` 값)로 보면 **`--disallowedTools Bash`는 메인과 서브에이전트의 Bash를 모두 차단**한다. 브리프 표의 "cli-disallowed | yes | no" 행과 대체로 같은 결론(사용 불가)에 도달하지만, "worker files" 열 자체는 2로 나와 표의 정확한 매칭은 아니다 — 이 지점은 브리프 예상 어느 행에도 정확히 들어맞지 않으므로 그대로 기록한다.

- **결론**: 이 환경(`--permission-mode dontAsk`, trusted workspace)에서 메인 세션만 선택적으로 잠그는 수단은 **없다**:
  - 커맨드 frontmatter `allowed-tools`: grant 힌트일 뿐 restrict 아님(무력).
  - CLI `--allowedTools`: dontAsk 아래에서 화이트리스트가 게이트로 작동하지 않음(무력, 워커까지 자유로움).
  - CLI `--disallowedTools`: 메인 세션 Bash를 확실히 막지만 **서브에이전트까지 동반 차단**되어 "메인만 잠그고 워커는 자유"라는 목표에 맞지 않음.
  - `permission_denials` 필드는 세 레그 모두 비어 있어 사후 판정 근거로 쓸 수 없다(자기보고 텍스트 + 훅 라인 유무로만 판정 가능했음).

- **결정**: 잠금 수단 = **없음(사후 검증)**. run-stage 단에서 메인 세션의 도구를 CLI/frontmatter로 선택적으로 제한하는 방법을 채택하지 않고, 스펙 §4.2.2가 이미 요구하는 **verify-stage 사후 검증**(워커가 만들어야 할 파일의 존재 여부, hooks.log의 `agent_id` 유무로 메인 세션 호출 vs 서브에이전트 호출 구분)에 의존한다. 이는 브리프 표의 "어느 모드든 no → verify-stage만" 행과 실질적으로 같은 결론으로 수렴한다.

- 비신뢰 측정은 무효: run [34574564725](https://github.com/LeeHyeonKyu/know-thy-build-demo/actions/runs/34574564725) / [34574709197](https://github.com/LeeHyeonKyu/know-thy-build-demo/actions/runs/34574709197)(스파이크 6, untrusted workspace)는 ADR-008이 보인 대로 untrusted 상태에서 allow가 무시되고 deny가 과잉 차단되는 조건에서 측정된 값이라 무효다. 본 ADR(spike-6b, trusted)의 값으로 대체한다.
