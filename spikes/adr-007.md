# ADR-007 idle ceiling

- default: elapsed **49s**, exit **0**, result에 `SPIKE_IDLE_OK` **yes**(마커는 있으나 `r` 필드가 `"Waiting for the background sleep task to finish; I will confirm once it completes."`로, **12분 sleep이 완주되지 않은 채 조기 반환**) · `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`: elapsed **56s**, exit **0**, result에 `SPIKE_IDLE_OK` **yes**(마커 있음, `r: "SLEPT"`로 완료를 주장)

  두 레그 모두 `--max-turns 5`·`--permission-mode dontAsk`로 브리프의 예상(default ~10분에 종료+결과 없음, 0에서 ~12분 후 OK)과 전혀 다르게 **1분 이내**에 종료됐다. `out.json`의 `duration_ms`는 default 1982ms, 0-leg 1554ms로 실제 벽시계 elapsed(49s/56s)와도 크게 어긋난다 — 이는 최상위 `-p` 프로세스가 `sleep 720` 서브에이전트를 실제로 끝까지 동기 대기하지 않고, 어느 시점에 백그라운드로 넘긴 뒤 그 시점까지의 상태를 "결과"로 보고했다는 뜻이다.
  - **default**: 정직하게 "아직 기다리는 중"이라고 보고 — 브리프가 기대한 "결과 없이 종료"와도 다르고(마커 자체는 있음) "정상 완료"와도 다른 **제3의 상태**(부분/placeholder 완료).
  - **0(무제한 기대)**: `r: "SLEPT"`로 **완료를 주장**하지만 elapsed(56s)가 `sleep 720`의 실제 소요 시간(≥720s)과 맞지 않아, 이 응답이 실제 12분 대기 후 확인된 값이라고 신뢰할 근거가 없다(spike-idle 워크플로에는 sleep 완료를 독립적으로 검증할 파일/마커가 없어 out.json의 자기 보고만으로는 실제 완료 여부를 확증할 수 없음 — 스파이크 설계상의 한계로 기록).

  ADR-006(spike-6)에서도 같은 CLI(2.1.268)로 `agent()`/`parallel()` 서브에이전트가 빠르게(수 초) 반환되면서 실제 작업(파일 쓰기, echo)을 완주하지 못하는 동일 패턴이 관측됐다 — 이는 브리프가 가정한 "idle ceiling이 무활동 시간을 재는 단일 파라미터"라는 모델이 이 환경/CLI 버전에서는 정확하지 않고, `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`가 0이어도 `-p` 세션이 서브에이전트 완료를 항상 동기 대기하지는 않는다는 것을 시사한다. 브리프의 3개 해석 분기(① default 조기종료+결과없음 → ceiling 실재, ② 0에서 완주 → 0=무제한, ③ default도 OK → ceiling 미적용) 중 어느 것에도 깔끔히 들어맞지 않는 **혼합/불확정 결과**로 기록한다. 브리프 규칙상 재시도는 "브리프가 예상한 실패 사유"에 한해 최대 2회이며, 이번 결과는 실행 실패(exit≠0, 타임아웃)가 아니라 exit 0의 "성공"으로 보고된 값의 신뢰도 문제이므로 재시도 대상이 아니라고 판단해 1회 실행(매트릭스 2레그)만으로 마감했다.

- **결정**: `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`을 CI 기본값으로 **고정**하되(0이 최소한 "더 오래 기다리려는 의도"를 표현하는 유일한 값이므로), 상한은 여전히 workflow의 `timeout-minutes`로 건다는 브리프의 원안은 유지한다. 단, **이 값만으로 서브에이전트 완료를 보장할 수 없다는 사실이 확인됐으므로**, 실제 완료 여부는 `-p`의 `result`/`stop_reason`을 신뢰하지 말고 워크플로가 만든 **부작용(파일/마커)을 사후 검증**해야 한다는 요구사항을 스펙에 추가해야 한다. 이는 ADR-006의 verify-stage 권고와 같은 결론으로 수렴한다.
