# ADR-008 신뢰되지 않은 러너에서의 deny

- project-only: deny 적용 **yes** · cli-settings: deny 적용 **yes** · trusted(hasTrustDialogAccepted): deny 적용 **yes**, allow 경고 사라짐 **yes**
  (세 매트릭스 레그 모두 `git ls-remote --heads origin deny-probe-should-never-exist`가 빈 출력으로 끝나 원격 브랜치가 전혀 생성되지 않았음을 확인. `force_push`는 3/3 "denied". 안전 프로브 결과 정리를 수행할 필요 없었음.)

  - **project-only** (프로젝트 `.claude/settings.json`의 `permissions.deny`만, `--settings` 없음, trust 부트스트랩 없음): `{"echo": "denied", "force_push": "denied"}` — **echo까지 함께 거부됨**. `permission_denials`에 두 Bash 호출 모두 기록(`tool_name: Bash`, 각각 `echo DENY_PROBE_MARKER...`와 `git push --force...`). "Ignoring 7 permissions.allow entries ... this workspace has not been trusted." 경고 여전히 출력. `num_turns: 3`. 모델의 최종 답변: "Bash 자체가 이 세션(don't-ask 모드)에서 차단되어 있어 둘 다 실행되지 않았다"는 취지로 스스로 원인을 보고.
  - **cli-settings** (`--settings .factory-ci-settings.json`으로 deny만 담긴 파일 추가 전달): `{"echo": "denied", "force_push": "denied"}` — project-only와 동일하게 **둘 다 거부**. `permission_denials`에 두 호출 모두 기록. "Ignoring 7 permissions.allow entries ..." 경고도 **여전히 출력**됨 — 즉 `--settings`는 project `.claude/settings.json`을 대체하지 않고 병합되며, project settings의 allow는 여전히 untrusted 사유로 무시된다. `num_turns: 3`.
  - **trusted** (`~/.claude.json`의 `projects[cwd].hasTrustDialogAccepted: true` 부트스트랩): `{"echo": "ran", "force_push": "denied"}` — **echo는 정상 실행**(`.spike/deny-probe.txt`에 `DENY_PROBE_MARKER` 기록됨 확인)되고 **force_push만 선택적으로 거부**됨. "Ignoring" 경고 **완전히 사라짐**(grep 결과 0건). `permission_denials`에는 force_push 호출 1건만 기록. `num_turns: 5`.

  **핵심 발견(관측 범위 한정)**: project-only·cli-settings 두 모드에서, **`/spike-deny` 커맨드(별도의 command-level `allowed-tools` 프론트매터 없음)로 실행한 이번 run들**에서는 `permissions.deny`가 있으면 (allow가 untrusted로 무시된 상태와 맞물려) `--permission-mode dontAsk`가 deny 패턴에 안 걸리는 `echo`까지 포함해 Bash 호출 전체를 거부했다. **단, 이 "Bash 전면 봉쇄"가 untrusted+deny 상태 전반에 성립하는 일반 규칙인지는 확정되지 않았다.** 동일하게 untrusted 상태이고 동일한 deny 규칙이 `.claude/settings.json`에 있었던 **ADR-006(Spike 6)**의 두 run(34574564725, 34574709197)에서는, `/spike-restricted` 커맨드(frontmatter에 `allowed-tools: Workflow(spike-hooks)`가 있음)로 실행한 non-매칭 Bash 호출(`echo MAIN_SESSION_BASH_RAN`)이 **ran**, `permission_denials: []`로 정반대 결과를 보였다(ADR-006 참조). 두 스파이크는 커맨드와 그 frontmatter가 다르므로 완전한 재현 실험은 아니며, 이 모순의 원인은 이 시점에서 **밝혀지지 않았다(단정하지 않음)** — Task 12(spike 6b, trusted)가 재측정할 예정이다. **trusted** 모드에서는 이번 관측에서 유일하게 allow가 정상 작동해 echo는 통과하고 deny만 선택적으로 걸리는 것이 확인됐다.

- **결정**: 이견 없이 확인된 사실만으로 판단한다 — (1) untrusted 워크스페이스에서는 `permissions.allow`가 항상 무시된다(ADR-002/ADR-008, 3/3 run에서 "Ignoring" 경고 확인), (2) `permissions.deny`는 테스트된 세 모드(project-only/cli-settings/trusted) 모두에서 대상 패턴(force-push)에 대해 100% 유효했다(3/3, 원격 브랜치 미생성으로 확인), (3) deny에 안 걸리는 일반 Bash 호출까지 막히는 "전면 봉쇄" 동작은 **untrusted + `/spike-deny` 커맨드에서만** 관측됐고, 같은 untrusted 상태의 다른 커맨드(Spike 6)에서는 반대로 통과가 관측돼 **원인 미상의 상충**이 있다. 이 사실들로부터: **trust 부트스트랩 스텝을 추가**하는 것을 권고한다 — trusted 모드는 이번 관측에서 유일하게 "allow 정상 작동 + deny 선택적으로만 적용"이 확인된, 상충 없는 모드이기 때문이다(사실 2). project-only/cli-settings를 그대로 쓰는 안은 "일반 Bash까지 막히는지"가 커맨드에 따라 달라질 수 있어(ADR-006과 상충, 원인 미상) Task 12 전까지는 **보류**한다. `~/.claude.json`에 `projects[$CLAUDE_PROJECT_DIR].hasTrustDialogAccepted: true`를 쓰는 스텝을 모든 factory CI 워크플로의 공통 setup(`setup-claude` 액션 또는 별도 `trust-workspace` 스텝)에 넣고, 그 위에서 project `.claude/settings.json`의 `permissions.deny`(L2)를 사용한다. `--settings .factory/ci-settings.json`는 trust 부트스트랩과 무관하게 project settings에 **병합**되므로 필수는 아니지만, deny 규칙을 워크플로별로 오버라이드/확장하고 싶을 때 보조 수단으로 유지할 수 있다.
- **스펙 영향**: §6.3에 다음을 명시 — "CI 러너는 각 워크플로 실행 전에 trust 부트스트랩(`hasTrustDialogAccepted: true`)을 거쳐야 한다. Untrusted 상태에서는 `permissions.allow`가 전부 무시되며(ADR-002/ADR-008), `permissions.deny`는 대상 패턴에 대해 유효하다(ADR-008, 3/3). 단, untrusted+deny 상태에서 deny에 안 걸리는 일반 Bash 호출까지 막히는지는 커맨드(및 그 `allowed-tools` frontmatter 유무)에 따라 다르게 관측되어(ADR-006과 상충, 원인 미상) 현재로서는 일반 규칙으로 명시하지 않는다 — Task 12(spike 6b, trusted)에서 재확인한다." §4.2.1의 4번째 플래그(신뢰 관련 플래그)는 `--settings` 단독이 아니라 "trust 부트스트랩 + project deny" 조합으로 기술.
